プロジェクトに小さな機能を追加しました。より大きな変更には、さらにしっかりとしたプロセスが必要です。GitHub Copilot app は組織の既存の開発フローに沿って作業できるように設計されており、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。Issue から新機能を作成し、コードの妥当性と機能の動作を確認した後、プロジェクトにマージします。

> [!NOTE]
> 機能のワークフローを進める間は、同じセッションを使用します。通常は作業するファイルの種類ごとに異なるセッションや PR を使いますが、ここでは主な概念に集中するため手順を簡略化します。

このレッスンでは、次の操作を行います。

- GitHub Issue から新しいエージェント セッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザー Canvas で機能を手動で検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の `quality-checks` スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増えているため、訪問者がカテゴリと発行元でゲームを絞り込めるようにします。バックログの Issue には機能の概要が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細があります。Plan モードで決定事項を整理してから、Autopilot に範囲を限定した実装を許可します。

## 背景

AI コーディング エージェントを開発フローに導入しても、基本的な考え方は変わりません。むしろ、より重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細を記載した Issue を開きます。
2. 実装する内容の計画を立てます。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プル リクエスト (PR) を作成します。
7. コードレビューが完了し、継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 具体的な手順はチームや組織によって異なりますが、ほとんどの場合は上記の流れを基にしています。

この標準的な進め方に従うことで、AI が生成したコードが要件を満たし、手作業で書いたコードと同じレビュー プロセスを通るようにできます。

## セッション モード

**セッション モード**では、エージェントがどこまで自律的に作業するかを制御できます。プロンプト フィールドの下にあるドロップダウンから設定し、いつでも切り替えられます。

- **Interactive**: エージェントが変更を提案し、次に進む前にユーザーの入力を待ちます。
- **Plan**: エージェントが計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律的にコードを書き、テストを実行し、ユーザーの入力を待たずに反復します。

まず Plan モードで計画を確認し、その後 Autopilot で実装します。

## Issue からセッションを開始する

開始する前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリ フォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。既存のシード済み Issue **Allow users to filter games by category and publisher** を開きます。新しい Issue を作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の Issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード セレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションから実行できない場合は、アプリの PATH またはバージョン管理ツールの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てると、Copilot がコードを書く前に進め方を確認できます。Issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして把握しています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、Issue の受け入れ条件と計画を照らし合わせます。カテゴリと発行元によるフィルター、アクセシブルなコントロール、データ アクセスの変更、テストが含まれていることを確認します。複数カテゴリの組み合わせや、該当するゲームがない場合など、不明確な動作について話し合います。

計画には、プロジェクトの既存ツールを使った lint、ユニット テスト、E2E テスト、型チェックを含めます。フィルターの実装とテストに範囲を絞り、品質ワークフローの完了後に PR を作成します。計画の修正は承認前に依頼し、後の検証に使えるよう Issue の URL と合意した明確化事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。承認しただけでモードが切り替わるとは限らないため、現在のモードを確認します。モード表示が **Autopilot** になっていることを確認してください。

Copilot が実装を開始します。計画に沿ってコードを生成し、テストを実行しながら、作業を反復します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係が不足している、またはポートが競合していると報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。自分で起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードは、ほかのコードと同じようにマージ前にレビューします。コードを確認し、サイトを実行して問題がないか確認しましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリと発行元の組み合わせも含め、結果を Issue と承認した明確化事項に照らし合わせます。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、ユニット テスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はプレビューをビルドして配信し、ローカル サーバーを再利用できます。以前のレッスンではなく、この worktree のサーバーがテスト対象であることを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動作するでしょうか。前と同じようにアプリを起動し、ブラウザー Canvas でサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザー Canvas で開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリを選択し、結果が一致することを確認します。フィルターを解除してから発行元を選び、結果を確認します。
4. カテゴリと発行元のフィルターを組み合わせ、結果を Issue と承認した計画に照らし合わせます。複数カテゴリをサポートする場合は、合意した組み合わせの動作も検証します。
5. 一致するゲームがない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットし、すべてのゲームが再表示されることを確認します。
6. 確認が終わったら、次のプロンプトでこのセッションが起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンに向けてセッションを保持する

まだフィルター機能の PR を作成またはマージしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はフィルター機能にカスタム指示を適用し、スキルと QA の改善を追加してから、レッスン 8 でまとめた PR を作成してマージします。開発サーバーを停止した後、セッションをアイドル状態にしておき、次のレッスンで同じセッションに戻ります。
